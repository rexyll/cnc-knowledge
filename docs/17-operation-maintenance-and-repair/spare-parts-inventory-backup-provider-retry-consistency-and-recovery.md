# 数控机床备件库存账本备份 Provider 重试、一致性与模糊提交恢复

**知识ID：** KNOW-000036  
**章节：** CH17 操作、维护与维修  
**状态：** IN_PROGRESS / 仅本地和Mock故障注入  
**适用范围：** 第二十轮Provider适配器、第二十一轮权限/分块能力之上的瞬态故障分类、重试和提交结果不确定性处理。

## 1. 目标与验证边界

本轮验证对象存储交互中的短暂限流、读后写延迟、写成功但响应丢失、分块上传响应超时、完成请求响应丢失、版本切换和重试耗尽等场景。目标不是“遇错就重试”，而是在明确瞬态错误范围内，以相同对象键、内容、版本或分块会话安全重试，确保最终状态可验证、不可确定时失败关闭。

实现位于 \`scripts/spare_parts_backup_storage_adapter.py\`，新增 \`ProviderTransientError\`。Mock通过注入参数模拟故障；不访问网络，不调用真实Provider。

## 2. Provider故障分类

### 2.1 可重试瞬态错误

Provider应将可恢复的限流、临时不可见、连接中断和超时映射为 \`ProviderTransientError\`，可以附带 \`retry_after_seconds\` 与 \`outcome_unknown\`：

- \`outcome_unknown=false\`：操作确定未提交或暂未可见，可按同一请求重试；
- \`outcome_unknown=true\`：服务端可能已提交，但响应未到达客户端。调用方必须使用原有幂等键/对象键/上传ID和完全相同内容重试，并在成功后读回校验，不能另建新备份ID或改变分块内容。

Mock故障钩子可以在服务端对象/分块实际写入后再抛出超时错误，以验证不确定提交的恢复路径。

### 2.2 不可重试错误

权限拒绝、路径不安全、对象键内容冲突、回执/负载摘要不匹配、缺失历史版本、分块序号非法、业务前置条件失败及其他永久性校验错误不属于可重试瞬态错误。当前 \`_provider_call()\` 只捕获 \`ProviderTransientError\`；普通 \`BackupStorageError\` 和完整性校验错误立即向上抛出，避免无意义重试或掩盖配置错误。

真实Provider适配器必须谨慎映射HTTP状态码/SDK异常：不能把所有超时、5xx或客户端异常一律当成同一错误类别；须区分是否已提交、请求是否可幂等重放，以及服务端是否支持条件创建。

## 3. 有界指数退避

适配器提供可配置参数：

- \`retry_max_attempts\`：总尝试次数，默认4（含第一次调用）；
- \`retry_base_delay_seconds\`：基础延迟，默认0.1秒；
- \`retry_max_delay_seconds\`：退避上限，默认2秒；
- \`sleep_fn\`：可注入等待函数，便于测试和运行时控制。

第n次重试的指数基准为 \`min(max_delay, base_delay * 2^n)\`。若Provider给出 \`retry_after_seconds\`，本轮使用不小于指数基准的等待值，但仍不超过配置的最大延迟。达到总尝试次数仍失败时，最后一个瞬态错误向上抛出。不会对权限拒绝、永久冲突或内容校验失败调用sleep/retry。

为保证CI和合成测试可重复，当前Mock适配器采用确定性退避、无随机抖动；生产Provider应结合并发规模、服务端Retry-After约束和供应商限流策略评审抖动方案、全局重试预算、熔断/隔离、请求超时与总操作deadline。默认0.1秒/2秒仅是代码默认，不是生产参数建议。

## 4. 读后写可见性

Mock支持对象写入后延迟若干次读取才对读请求可见。延迟读取以瞬态错误返回，适配器按预算重试；在预算内变为可见后，必须继续校验对象长度、SHA-256、备份回执和原始账本语义。

若可见性延迟超过重试预算，适配器不得返回PUBLISHED/VERIFIED/RESTORED。此时服务端可能已有对象，故障恢复的正确路径是稍后以原backup ID查询、读取并验证，不得擅自创建一个不同ID的“替代备份”掩盖原状态。盘点应保留该前缀及请求关联证据。

真实Provider必须明确对象写入确认、回执可见、版本清单可见和跨区域副本可见的语义。Mock强一致/延迟可见模拟不能证明云服务或复制目标的实际一致性等级。

## 5. 写成功但客户端超时：幂等恢复

Mock支持在第N次新对象成功落盘后故意抛出 \`ProviderTransientError(outcome_unknown=true)\`。适配器对同一key和相同字节重试；Mock的 \`put_if_absent\` 返回已经存在的同内容对象，不重复创建对象。第二十轮的最后回执仍是多对象备份包的提交标记，因此回执写入成功但响应丢失时，重试会先确认同一回执已存在，再重新读取并验证所有负载。

分块场景也遵循同样规则：
- 分块写入后超时：同一upload ID和part number重试，返回同一摘要；
- 完成对象已创建但完成响应丢失：以原upload ID重试完成操作，若对象字节一致则确认已完成并清理会话暂存；
- 内容不同、分块校验或对象摘要不符：冲突失败，不覆盖对象。

此行为依赖真实Provider支持条件创建或等价幂等语义。若供应商对同一对象键的重复PUT会无条件覆盖，Provider必须先实现安全的条件写入层，否则不能接入当前适配器。

## 6. 对象版本切换和固定版本读取

当Provider声明对象版本控制时，回执记录每个负载对象的version ID，恢复/验证必须读取该精确版本，而不是默认读取当前最新版本。Mock可模拟同一key出现更新版本；历史版本仍存在时，旧备份验证应继续成功。若回执所指历史版本已不可读/被清理，验证必须失败关闭，不能静默回退到新版本。

真实Provider需要证明版本ID不可混淆、版本读取受授权保护、对象锁/保留策略能覆盖恢复窗口，以及版本删除/生命周期策略不会提前清除仍被备份清单引用的历史版本。

## 7. 限流、重试耗尽与恢复流程

建议真实Provider适配器按下列顺序处理：

1. 依据供应商错误码/SDK错误将异常映射为瞬态或永久错误，记录是否存在提交结果不确定；
2. 对可重试请求维持相同backup ID、对象键、upload ID、part number和内容摘要；
3. 遵守配置的最大尝试次数、延迟上限、单次超时和总deadline；记录attempt、延迟、request ID和最终状态；
4. 重试耗尽后标记UNKNOWN/RETRY_EXHAUSTED，不声称备份成功；保留对象前缀和审计关联；
5. 后续恢复由显式盘点/验证命令以原ID回读，验证回执与所有对象后再决定是否继续，不自动生成新的备份ID；
6. 任意摘要不一致、版本缺失或权限错误均停止，不以重试掩盖安全或数据损坏问题。

CI测试不应依赖真实等待；通过注入sleep函数验证延迟序列、预算和不重试路径。
