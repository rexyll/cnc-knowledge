# 数控机床备件库存账本备份 Provider 公平调度、租户配额与任务取消/截止时间

**知识ID：** KNOW-000038  
**章节：** CH17 操作、维护与维修  
**状态：** IN_PROGRESS / 仅本地与Mock并发调度验证  
**适用范围：** 在既有Provider熔断、舱壁和聚合重试预算之上，为单个Adapter实例增加任务上下文、公平排队、租户并发上限和协作式取消/截止时间控制。

## 1. 目标与边界

本轮解决多个备份/恢复/验证/盘点任务竞争同一Provider操作域时的排队公平性和资源隔离问题。调度器只分配本地Adapter中的操作域并发槽位，不代表分布式调度服务、跨进程配额或集群任务编排。

任务上下文由调用方显式提供：`task_id`、`tenant_id`、整数 `priority`、可选超时以及可选线程安全取消事件。未显式创建上下文的旧调用继续使用隐式默认任务和默认租户，保持原有接口兼容。

**优先级约定：** 数值越大，调度优先级越高；调度器不内置恢复高于备份、备份高于盘点等业务分类。任务类别与优先级映射必须由部署方/业务责任人批准并由调用方传入。优先级和租户标识是调度元数据，不改变备份对象键、内容、回执或业务状态。

## 2. 公平排队和防饥饿

每个操作域（read/write/multipart/inventory）独立维护有界并发计数和等待队列。调用方设置 `bulkhead_acquire_timeout_seconds=0` 时仍采用快速失败；设置正数时允许在该上限内等待。

有可用槽位时，调度器只从当前租户配额允许的等待者中选取下一项，按以下规则排序：
1. 基础优先级为调用方的整数priority；
2. 等待时间每经过一个配置的aging interval，effective priority增加一个单位；
3. effective priority相同时按入队顺序先到先服务。

等待时间持续提高有效优先级，使长期等待任务有机会超过后来入队的高优先级任务，避免有限优先级差下的永久饥饿。此机制不承诺严格的最大等待时延；若业务需要硬实时调度，需要另外定义可验证的截止时间、到达模型及容量边界。

当前默认 `priority_aging_interval_seconds=1.0`，仅为实现基线，不是生产推荐。所有优先级/老化参数都应通过实际任务到达分布和业务服务等级评估。

## 3. 租户并发配额

Adapter可配置 `tenant_bulkhead_limits`，按tenant ID限制每个操作域内同一租户的并发调用数；可通过 `tenant_bulkhead_default_limit` 为未显式列出的租户设置默认上限。未配置时，租户有效上限等于该操作域容量。

配额按操作域分别计数，不是跨read/write/multipart/inventory的全局总额度；一个租户在read域占满不会阻塞其write域，也不会占用另一租户的名额。租户配额只约束同一个Adapter实例，不能替代API网关、队列服务或Provider端的账号级限制。

调度器不推断tenant ID，不接受空租户标识。真实项目需要由可信身份上下文提供租户身份，不能直接信任外部请求任意声明的租户字段。

## 4. 取消与任务截止时间

`task_context()` 可携带：
- `cancellation_event`：提供 `is_set()` 的线程安全取消事件；
- `timeout_seconds`：任务启动时基于单调时钟计算任务截止时刻；
- `task_id`：供异常诊断使用；
- `tenant_id` 和 `priority`：用于调度隔离。

调度器在获取槽位前、排队等待期间、调用Provider前、Provider返回后以及每次重试/退避边界检查取消和deadline。排队中的取消会移除等待项并释放队列位置；取消/超时为终止错误，不会继续重试或作为Provider可用性故障累计到熔断器。

**同步调用限制：** 当前Provider Protocol没有标准化的中断/取消参数，因此无法强行终止已经进入的同步Provider调用。取消和deadline只在控制边界协作生效；底层网络请求仍需由未来Provider实现配置连接/读写超时和原生取消能力。超时不等同于Provider提交失败，也不能据此创建新backup ID掩盖未知提交状态。

## 5. 与现有熔断、舱壁和重试预算的组合

一次调用的处理顺序为：检查任务取消/deadline → 排入公平舱壁并满足租户配额 → 申请对应操作域熔断器 → 执行Provider callback → 记录熔断结果并释放并发槽位 → 检查任务状态 → 消耗重试预算 → 进行可取消的有界退避。

优先级队列不会改变CircuitBreaker状态机、半开探测配额、同域容量、任务RetryBudget或对象级幂等重试身份。控制异常均快速失败，不会被误识别为可重试的ProviderTransientError。

## 6. 自动化测试和验收范围

新增5项专项unittest，验证：
- 正常排队情况下，高优先级等待者先进入槽位；
- aging使较早入队的低优先级任务最终越过后来任务，避免持续饥饿；
- 单租户配额达到上限时拒绝该租户新增并发，同时允许另一租户使用独立容量；
- 等待期间取消会移除队列项且不调用Provider；
- deadline在重试退避期间到期时阻止下一次Provider尝试。

测试使用线程、Event和注入单调时钟/等待函数，不访问网络、云账户、真实身份服务或企业系统。

**生产限制：** 公平性和配额只在单Adapter/进程内生效；多个实例之间没有协调。没有真实Provider请求取消、客户端超时、跨进程/容器配额、租户公平性、生产任务优先级或负载压测证据。生产备份仍关闭，`governance_readiness=BLOCKED_PENDING_ENTERPRISE_APPROVAL`，`business_rule_assertions=NOT_EVALUATED`。
